# M0 review: walking skeleton

Reviewer: senior reviewer. Pass: first review.
Scope: `git diff main...m0-walking-skeleton` excluding `design/` (code as of `e6f2269`).
Gates run locally: `pnpm lint`, `pnpm typecheck`, `pnpm test` green; `pnpm test:integration` green (db 10, api 3) against ClickHouse 26.8.34.13. CI on PR #1 green.

## Findings (most severe first)

### R-M0-01 Schema accepts numbers the storage path cannot hold (must fix, backend)
**Where:** `packages/schema/src/events.ts:71` (`count`), `:80` (`ts: count`), and every `count` field that lands in a `UInt32` column (`startup_ms` :99, `connect_ms` :101, `duration_ms` :111/:124/:152, `seq` :119, `action_seq` :170); `packages/db/src/insert.ts:10-12`.
**Problem:** `count` is `z.int().nonnegative()`, which only caps at 2^53. Checked locally:
- `ts: 9e15` passes `FleetEvent`, then `toClickHouseDateTime` throws `RangeError: Invalid time value`. Rows are built before any INSERT, so one bad event fails the whole `insertEvents` call. Once the M1 buffer is in place, that means up to 5k events from every client.
- `ts` in seconds (`1_760_000_000`) passes and becomes `1970-01-21 08:53:20.000`. The 30-day TTL then deletes it (the integration test comment at `db.integration.test.ts:277` relies on this), so the data is lost with no error. If a batch has wild clocks spread over more than 100 days, it also hits `max_partitions_per_insert_block = 100` and the whole INSERT fails.
- `UInt32` columns wrap without an error: `SELECT * FROM format(JSONEachRow, 'x UInt32', '{"x": 5000000000}')` returns `705032704`. A duration over about 49.7 days would be stored as a wrong number.

**Fix:** In `events.ts`, add `const uint32 = z.int().nonnegative().max(4_294_967_295)` and use it for every field stored as `UInt32`. Bound `ts` to a plausible window in ms, for example `z.int().min(Date.UTC(2020, 0, 1)).max(Date.UTC(2100, 0, 1))`; this also catches seconds sent instead of milliseconds. Add a unit test at each boundary. In M1, ingest should also reject `ts > now + small skew`, which needs the server clock and doesn't belong in the schema.

### R-M0-02 Turbo cache ignores changes in internal packages, so local `typecheck`/`test` can pass on stale results (must fix, platform)
**Where:** `turbo.json:20-22`.
**Problem:** `typecheck` and `test` have no `dependsOn`, and internal packages ship TS source with no build task. `turbo run typecheck test --dry=json` shows `@fleetscope/api#typecheck deps=[]`, and its inputs are only the 13 files under `apps/api`. Changing `packages/schema` or `packages/db` therefore leaves `api`/`db` typecheck and test as cache hits. `pnpm lint && pnpm typecheck && pnpm test` is our definition of done (CLAUDE.md), so it can report green locally on code that no longer compiles. CI isn't affected today only because it doesn't persist `.turbo`.
**Fix:** Use Turborepo's documented "transit node" pattern for just-in-time packages:
```json
"transit": { "dependsOn": ["^transit"] },
"typecheck": { "dependsOn": ["transit"] },
"test": { "dependsOn": ["transit"] }
```
Then check it: edit a file in `packages/schema`, run the dry run again, and confirm that `api#typecheck` now lists a dependency and gets a new hash.

### R-M0-03 Claude PR review job cannot post its review (must fix, platform)
**Where:** `.github/workflows/claude.yml:54-70`.
**Problem:** Setting `prompt` puts `claude-code-action@v1` into automation mode. In that mode the comment tools must be allowed explicitly; the action's own PR-review example passes `--allowedTools` for the inline-comment MCP tool and `gh pr comment/diff/view`. Without them, once `ANTHROPIC_API_KEY` is set the job runs, spends tokens and posts nothing. Confidence: high, but it can't be verified until the key exists. P5's "skips cleanly without a key" is met.
**Fix:**
```yaml
claude_args: |
  --max-turns 10
  --allowedTools "mcp__github_inline_comment__create_inline_comment,Bash(gh pr comment:*),Bash(gh pr diff:*),Bash(gh pr view:*)"
```
When the key is added, check on a throwaway PR that a comment actually appears.

### R-M0-04 ClickHouse client logs plain multi-line text to stderr, outside pino (nit, backend)
**Where:** `packages/db/src/client.ts:116-122`.
**Problem:** `@clickhouse/client` uses its own default console logger. The integration run prints `[...][WARN][@clickhouse/client][Connection] Ping: HTTP request error.` followed by a multi-line `Caused by:` stack. In production every failed `/healthz` probe during an outage would emit non-JSON lines, which breaks the "pino (JSON)" convention and log parsing.
**Fix:** Pass `log: { LoggerClass }` to `createClient`, with a small class that forwards `trace/debug/info/warn/error({ module, message, args, err })` to a pino child logger. At minimum, set `log.level` so ping failures aren't logged twice (the API already logs `healthz: ClickHouse is down`).

### R-M0-05 `sessions` has no partition and no TTL (nit, backend)
**Where:** `infra/clickhouse/0001_sessions.sql:26-27`.
**Problem:** The table is ordered only by `session_id`, so the M2 Sessions list filtered by time range has to scan the whole table. It also has no retention, so session rows outlive their actions, samples and issues after 30 days, and Session detail would show sessions with no data. A partition key can't be changed later without rebuilding the table, and the table is empty now.
**Fix:** Add `PARTITION BY toYYYYMM(started_at)` and a TTL that is deliberately matched to the raw tables (for example `TTL toDate(started_at) + INTERVAL 30 DAY`). This is safe for ReplacingMergeTree because both versions of a row share `started_at`: `endedSessionRow` copies it. Add a comment saying that invariant must hold. ORDER BY stays `session_id`, as in PLAN §6.

### R-M0-06 TTL rewrites parts instead of dropping them (nit, backend)
**Where:** `infra/clickhouse/0002_actions.sql:19-22` and the same lines in 0003, 0004, 0005; `docs/adr/0001-clickhouse.md:43`.
**Problem:** The ADR says the TTL "drops old raw partitions", but without `ttl_only_drop_parts = 1` ClickHouse expires rows through TTL merges. Partitions and TTL are both per day here, so dropping whole parts is the cheap option.
**Fix:** Add `SETTINGS ttl_only_drop_parts = 1` to the four raw tables.

### R-M0-07 Orphaned `session.ended` is dropped permanently, and inserts aren't atomic across tables (nit, backend, M1 follow-up)
**Where:** `packages/db/src/insert.ts:228-233`, `:235-244`.
**Problem:** I'm not reopening the "count, don't invent" decision; it's correct for M0. In M1, though, a `session.started` flush that fails and is retried later turns the earlier `ended` into an orphan. That ended event is then gone for good, and the session shows `running` forever, which presents a finished session as live. Separately, `insertEvents` writes `sessions` first and the raw tables after it. If an INSERT fails partway, a retry duplicates whatever was already written, until event_id dedupe exists.
**Fix (M1):** Have the ingest buffer keep orphaned ends and retry the merge on the next flushes for a grace window (for example 60s). Then log `orphanedEnds` at `warn` with the session ids. Note the partial-write case in the M1 dedupe design.

### R-M0-08 Stored session state `"running"` is defined only in `db` (nit, backend)
**Where:** `packages/db/src/insert.ts:74`, `infra/clickhouse/0001_sessions.sql:20`.
**Problem:** API shapes must come from `packages/schema`. When M2 exposes session status, `"running" | SessionStatus` would otherwise get redefined in `api`/`web`.
**Fix:** Export `SESSION_STATES = ["running", ...SESSION_STATUSES]` and a `SessionState` enum from `packages/schema`, and use it in `runningSessionRow`/`SessionRow.status`.

### R-M0-09 Undocumented limits of the migration runner (nit, backend)
**Where:** `packages/db/src/migrate.ts:75-82`, `:148-169`.
**Problem:** The runner has no lock, so two runners at once (for example two deploy replicas in M5) can both apply a file and record it twice. If a multi-statement file fails partway, its earlier statements re-run on the next attempt. Both cases are fine today because every statement is `CREATE TABLE IF NOT EXISTS`, but nothing says future migrations must stay that way.
**Fix:** Extend the doc comment, or add `infra/clickhouse/README.md`, saying: one runner at a time (migrate as a single release step, never on API startup), and every statement must be idempotent (`IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`) or each file must hold a single statement.

### R-M0-10 Integration tests depend on order (nit, backend)
**Where:** `packages/db/src/db.integration.test.ts:264-272`, `:286-319`.
**Problem:** "stores unsupported metrics as NULL" only passes because the previous test seeded the database. The two session tests delete and rewrite seed sessions that earlier tests asserted on. Running one test (`-t`) or reordering them breaks the suite.
**Fix:** Each test seeds what it needs, or uses its own session ids, in a `beforeEach` or inline.

### R-M0-11 Dependabot doesn't update the ClickHouse image (nit, platform)
**Where:** `.github/dependabot.yml:26-31`.
**Problem:** The `docker` ecosystem looks for Dockerfiles; `infra/` only has `docker-compose.yml`. Compose files need `package-ecosystem: docker-compose`. Even after that change, the CI service tag in `ci.yml:35` can only be kept in sync by hand.
**Fix:** Switch to `docker-compose`. Add a CI step that fails when the two tags differ (a one-line `grep` comparison), or note in the PR template that a compose bump PR must also edit `ci.yml`.

### R-M0-12 CI never builds (nit, platform)
**Where:** `.github/workflows/ci.yml:24-26`.
**Problem:** `next build` and the api esbuild bundle (`apps/api/build.mjs`) aren't checked in CI. A broken api bundle would only show up at deploy time in M5.
**Fix:** Add `- run: pnpm build` to the `check` job.

### R-M0-13 `.gitignore` lets most `.env.*` files through (nit, platform)
**Where:** `.gitignore:15-18`.
**Problem:** Only `.env`, `.env.local` and `.env.*.local` are ignored, so `.env.production` or `.env.test` holding real credentials could be committed. gitleaks would probably catch it, but only after the push.
**Fix:** Use `.env*` and `!.env.example`.

### R-M0-14 Third-party actions that get secrets aren't pinned to SHAs (nit, platform)
**Where:** `.github/workflows/claude.yml:54`, `:106`; `.github/workflows/ci.yml:71`.
**Problem:** `anthropics/claude-code-action@v1` runs with `ANTHROPIC_API_KEY` and `contents: write`. `gitleaks/gitleaks-action@v3` gets `GITHUB_TOKEN`. Anyone who can move a tag can change what runs with those secrets; the tj-actions incident is the standard example.
**Fix:** Pin these two to full commit SHAs with a `# vX.Y.Z` comment. The existing Dependabot `github-actions` config keeps SHA pins up to date.

### R-M0-15 Biome runs twice in `pnpm lint` (nit, platform)
**Where:** `package.json:14`.
**Problem:** `biome check .` at the root already covers every package, and then `turbo run lint` runs it again for each package.
**Fix:** Keep one: either root-only (`"lint": "biome check ."`, then drop the package `lint` scripts) or turbo-only (also lint root files by adding root-level config files to the root check).

## Checked and fine
- `claude.yml` uses `pull_request`, not `pull_request_target`. Fork PRs and Dependabot are skipped. `@claude` is gated on OWNER/MEMBER/COLLABORATOR, and the action checks write access too. Permissions are scoped per job. The job skips cleanly without the key.
- The CI ClickHouse service matches compose (image tag, user/db env, ulimit, healthcheck). `--frozen-lockfile` is used and the pnpm version comes from `packageManager`.
- DDL matches PLAN §6: engine, ORDER BY, daily partitions, 30-day TTL, `LowCardinality` on low-cardinality columns, and `Nullable` only where the schema allows null.
- Every dynamic query is parameterized (`{database:Identifier}`, `{ids:Array(String)}`, `{table:Identifier}`), and the database name is also checked against an identifier regex.
- Writes are batched: one INSERT per table per `insertEvents` call.
- `toClickHouseDateTime` is correct for in-range values. `toISOString` is always UTC and the columns are `DateTime64(3, 'UTC')`; `toString(started_at)` in the lookup comes back in the same format, and the ms round-trip has an integration test.
- The migration runner sorts files, rejects bad names and duplicate numbers, checks checksums of applied files, fails on a missing applied file, and doesn't record a failed file. `.gitattributes eol=lf` keeps checksums stable on Windows.
- `/healthz` is bounded twice (the ping's `AbortSignal` and a race timeout), has unit tests for down/throw/slow and integration tests for unreachable and bad credentials, and sets `no-store`.
- Env validation fails fast and lists every bad variable. There is no `console.*` in committed code (Biome `noConsole: error`).
- Schema tests are behavior-focused: one valid and one invalid case per type, batch limits, and the null-vs-missing distinction.
- The ADR covers why ClickHouse and when Postgres is still the right choice.
