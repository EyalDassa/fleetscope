## Findings (most severe first)

### R-M2-01 The Overview runs the full `session-facts` query 13 times per refresh, which is why it is slow (must fix, dashboard + platform)

**Where:**
- `infra/grafana/dashboards/fleetscope-overview.json`: the seven single-number panels at `:154, :267, :428, :613, :690, :1049, :1147`, plus `:1225` (Error rate), `:1733` (By engine), `:2313` and `:2620` (the two failure tables).
- `fleetscope-sessions.json:276`.
- `fleetscope-session.json:146, :247, :1035`.

**Problem.** Each pasted `session-facts` block does a lot:
- It reads `sessions FINAL`, aggregates `issues` and `actions`, aggregates the `pricing_current` view, and makes three hash joins.
- `picked` is referenced five times, and ClickHouse inlines CTEs instead of materializing them.
- By engine references `facts` three times (`per_engine`, the id list in `peaks`, `causes`), so the whole block runs three times. The Sessions table references it twice (main query and `peaks`).

Measured on the local data (54 sessions, 581 actions; server time, median of 5):

| Query | Server time |
|---|---|
| `picked` alone (`sessions FINAL` with the filters) | 7 ms |
| One KPI panel (`session-facts` + `count()`) | 64-91 ms |
| Recent failures | 75 ms |
| Sessions table | 212-224 ms |
| By engine | 262-321 ms |
| **One query returning all 11 KPI-row values** (both windows via `countIf`) | **84 ms** |

So the Overview costs about 1.1 s of ClickHouse time every 30 s (ten panels at about 75 ms each, plus By engine), before plugin and HTTP overhead for 17 requests. Almost all of it is the same per-session work repeated. With M3's 500+ simulated sessions (and QA's 10k), it grows with every copy.

**Fix:**
1. **KPI row from one query (dashboard).**
   - "Fleet verdict ↗" (id 1) runs a summary query over one `facts` and returns one row:
     - by `ended_at`: `verdict, ended, success_rate, healthy, degraded, failed, blocked, interrupted`;
     - by `started_at`: `sessions, simulated_share, estimated_cost_usd`.

     Each column uses its own `countIf` window. I ran exactly this query: 84 ms.
   - Outcomes, Simulated share, Sessions, Success rate, Estimated cost and Interrupted switch to Grafana's Dashboard data source:
     - `"datasource": {"type": "datasource", "uid": "-- Dashboard --"}`, target `{"panelId": 1, "refId": "A"}`;
     - each picks its column with `options.reduceOptions.fields` (`/^sessions$/` and so on; Outcomes uses `/^(healthy|degraded|failed|blocked)$/`).
   - Field configs, mappings and data links stay as they are.
   - Optional: do the same for Active now / CPU / Memory (one query), and on Session detail for Status / What happened / Est. cost (the What happened query can also return `display_status` and `est_cost_usd`).
2. **By engine and Sessions read `facts` once (dashboard).**
   - Fold the top cause into `per_engine`. For example, `groupArrayIf(cause, <ended in range> AND cause IS NOT NULL) AS causes`, then `arrayReduce('topK(1)', causes)[1]` and `countEqual(causes, top_cause)`. Any single-pass form is fine.
   - In both `peaks` CTEs, take the session ids from `sessions FINAL` with the panel's filters, not from `facts` (7 ms instead of about 75 ms).
3. **Optional at this scale, worth it at 10k sessions (dashboard + README snippet).** Add `AND engine IN (${engine:singlequote}) AND source IN (${source:singlequote})` to `issue_facts` and `action_facts`. The raw tables are ordered by `(engine, session_id, ts)`, so with no `engine` condition ClickHouse cannot use the leading key column to narrow the `session_id IN (...)` lookup.
4. **Check support (platform).** `grafana:check` must:
   - accept `-- Dashboard --` panels;
   - check that `panelId` exists and has a SQL target;
   - check that every field a panel selects (the `reduceOptions.fields` regex, `byName` overrides) is a column the source query returned. `runQuery` already returns `columns`.
5. **Docs (lead).** ADR 0003 ("Dashboards copy them") and DESIGN 9 ("every panel uses UID `fleetscope-clickhouse`") need the exception; see R-M2-16.

**The lead's question: is the Dashboard data source simpler than 10 copies?**
- **Yes for the seven single-row stats.** One query, one place for the KPI definitions, six fewer 70-line copies. The cost: if that query fails, seven panels show the error instead of one.
- **No for the tables and time series.** They need different shapes and windows. Sharing would mean Grafana transformations, which are harder to read and which the CI SQL check doesn't cover.
- **A ClickHouse parameterized view** for `session-facts` would remove the copies, but not the runtime cost. I'd only consider it if the copies keep growing in M3/M4.

**Done when:**
- The Overview runs `session-facts` at most 5 times per refresh (KPI summary, Error rate, By engine, Recent failures, Top failure causes).
- By engine and the Sessions table are each under about 120 ms on the local data.
- The lead sees the Overview render in about 2 s or less locally.

### R-M2-03 Drill-downs can miss the sessions behind the number (must fix, dashboard)

**Where:**
- `fleetscope-sessions.json:276`: the outer `WHERE $__timeFilter(f.started_at)`, and `peaks` with `ts >= $__fromTime`.
- The "Running sessions" links in `fleetscope-overview.json` (`:562`, `:921`, `:998`) use `from=now-15m`.

**Problem:** the Sessions table lists sessions that started in the range. The numbers that link to it often use another window.
- Verdict, Outcomes, Success rate, Error rate, Interrupted and Top failure causes count sessions that **ended** in the range. A failure that started before `from` is counted but not listed.
- Active now / CPU / Memory link with `from=now-15m&var-status=running`. A session that has been running for more than 15 minutes is counted but the list is empty. This will happen with `long-idle-session` in M4, and with zombies.

PLAN principle 1 ("every number links to the sessions behind it") and the done-when ("drill-down Overview → Sessions → Session detail works") both need these to agree.

**Fix (simplest):** list every session that overlaps the range. `facts` already holds exactly those (it is `picked`'s filter: `started_at <= $__toTime AND (ended_at IS NULL OR ended_at >= $__fromTime)`). So:
- drop `$__timeFilter(f.started_at)` from the outer WHERE;
- in `peaks`, bound `ts` by the listed sessions' `started_at`, not by `$__fromTime`, so a session that started before the range still gets its whole peak;
- change the description to "Sessions that ran at any time in the range (started, ended or still running), newest first".

The list then contains every session behind every link. Its row count can be slightly higher than the Sessions KPI (started in the range); the description explains why.

**Alternative:** a visible custom variable `window` (`started` / `ended`), set by the outcome links with `var-window=ended`. It is exact, but it's one more variable.

### R-M2-04 "Active now" uses 30 s on the dashboards and 5 minutes in the README (must fix, backend)

**Where:**
- `packages/db/README.md:217-235` (`fleet-in-use-now`, "no sample in the last 5 minutes", `INTERVAL 5 MINUTE`) and its test, `packages/db/src/dashboard-sql.integration.test.ts:501`.
- The dashboards use 30 s in four places: overview `:536`, `:895`, `:972` and the `running` CTE in `:1733`. DESIGN 4.2 also says 30 s.

**Problem:** the README says it is the source of truth for the definitions, and that if it and DESIGN disagree, they're fixed together.

**Decision: 30 s is right.**
- A live session's newest sample is normally at most about 4 s old: one sample every 2 s, a 1 s collector flush, a 1 s API flush.
- 30 s tolerates a short ingest stall and matches the 30 s refresh.
- 5 minutes would keep counting a dead runner's containers (CPU, memory, "active") for 5 minutes after they're gone.
- The cost: during an ingest outage longer than 30 s, Active now drops to 0. That's an honest reading of "no data now".

**Fix:** change the README snippet and its prose to `INTERVAL 30 SECOND`, give the reason in one sentence, and update the test's sample times.

### R-M2-07 The rollup backfill can erase history, and on ClickHouse Cloud it may be dropped as a duplicate (nit, backend; second half unsure)

**Where:** `packages/db/src/rollups.ts:40-49`; README "Backfill".

**Problem:**
1. `TRUNCATE` wipes `fleet_minute` back to what the raw tables still hold (30 days). The README says so, but nothing stops a run at month 6 from deleting five months of a 1-year rollup.
2. (Unsure.) On ClickHouse Cloud, tables are SharedMergeTree and insert deduplication is on by default. A second backfill re-inserts the same `INSERT … SELECT` blocks after a TRUNCATE, and those may be dropped as duplicates, leaving the rollup empty. The local integration test can't see this, because a local MergeTree without a dedup window doesn't deduplicate.

**Fix:**
1. Rebuild only from the oldest raw minute:
   - compute `from = min(toStartOfMinute(ts))` over `actions` and `resource_samples`;
   - delete only `minute >= from` (`ALTER TABLE fleet_minute DELETE WHERE minute >= {from}`, or drop the whole months);
   - add `WHERE ts >= {from}` to both SELECTs.

   Or refuse to run when `fleet_minute` has rows older than `from`, unless `--force` is given.
2. Pass `clickhouse_settings: { deduplicate_insert: "disable" }` (the setting `insertEvents` already uses) on the two inserts.

## Answers to the lead's questions

**Dashboard SQL against the README rules:**
- **Interrupted sessions.**
  - Excluded from: the verdict, Outcomes, Success rate, the Error rate chart, By engine (success rate, top cause), Recent failures, Top failure causes and the cause filter.
  - Included in: Sessions, Interrupted, browser-hours and cost.
  - The `fleet_minute` metrics (p95, actions/min) include their actions, as the README says.
  - The SQL matches how the runner marks a Ctrl+C session: `failed` + `interrupted` (`apps/fleet-runner/src/outcome.ts:38`).
- **Denominators.** `ended = countIf(NOT is_interrupted)` over `ended_at IS NOT NULL AND $__timeFilter(ended_at)`, so running sessions are out through `ended_at`. `succeeded = healthy + degraded = status 'success'`. The error rate is the same denominator. Correct everywhere.
- **`ended_at` vs `started_at`.** Each query uses the right window. The descriptions are wrong in places (R-M2-02), and the list behind the links uses a narrower window (R-M2-03).
- **Cost NULLs.** A session is NULL when it has no price (`price.provider = ''`). Totals are NULL when any session is unpriced (R-M2-14). The empty set gives $0. The NULL-unpriced logic depends on `join_use_nulls = 0` (R-M2-06).
- **`ifNull(x, 0)`.** None. The check enforces this. The only implicit zeros are counts from the LEFT JOINs (`actions`, `failed_actions`, `issue_count`), and 0 is correct there.
- **Active now window.** 30 s (R-M2-04).

**Performance:**
- The cost is repeated per-session work (R-M2-01).
- Pruning on the time filters:
  - `fleet_minute` (month partitions, `ORDER BY (engine, source, minute)`) and the "now" queries on `resource_samples` (`ts >= now() - 30 s`, `engine IN`) prune well.
  - `sessions FINAL` reads every daily partition up to `to`, since there's no lower bound. Fine for that small table.
  - `issues` and `actions` are pruned by `ts >= min(started_at)`. They don't use the `engine` key column (R-M2-01, fix 3), and zombies defeat the pruning (R-M2-18).
- The Dashboard data source vs copies: see R-M2-01.

**`fleet_minute`:**
- **The views and reads are correct.** The views write `-State` (`countState`, `countIfState(NOT ok)`, `quantilesState(0.5, 0.95)`, `sumState`); every read uses `-Merge` with `GROUP BY`, and the `quantilesMerge` parameters match the state.
- **Averages.** Averages are sum / count with a zero guard. The samples view only takes rows with both values, so the divisor is right.
- **Retention.** Month partitions with `ttl_only_drop_parts` drop whole expired months, as intended.
- **Backfill.** The backfill SELECTs are tied to the view text by a unit test, and the integration test shows the backfill gives the same numbers as the views.
- **Insert deduplication.**
  - A deduplicated raw insert also skips the views. That's ClickHouse's default (`deduplicate_blocks_in_dependent_materialized_views = 0`), so a retried flush can't double-count.
  - `fleet_minute` itself has no dedup window, so two identical aggregated blocks are never dropped by mistake.
- Remaining concerns: R-M2-07.

**The read-only user:**
- `readonly = 1` with exactly `max_execution_time` (60, max 300) and `additional_table_filters` as `CHANGEABLE_IN_READONLY`. `GRANT SELECT ON <db>.*` only.
- The password is sent as a query parameter. Checked: it is not in `query_log`, and the request log shows `[HIDDEN]`. The CLI silences the client logger, and error messages are redacted.
- The dev password is refused for non-local URLs; the admin's own name and `default` are refused.
- Locally the user cannot read system tables.
- **Injection through the textbox variables** (`session`, `cause`): Grafana's `singlequote` doesn't escape backslashes, so a crafted value can break out of the string. But any Viewer can already send arbitrary SQL to `/api/ds/query`, so the read-only user is the real boundary, and it holds. No finding.

**`grafana:push`:**
- HTTPS only, except to loopback hosts.
- The token travels only in the `Authorization` header and is never printed. The password only goes in `secureJsonData` and is printed as `********`.
- A loopback ClickHouse URL for a remote Grafana is refused; a localhost API URL only gets a warning.
- Everything is built and checked before the first write, and nothing is deleted.

**Trace endpoint and Perfetto page:**
- `SessionId` (zod) is validated; 400, 404 and 500 responses never include details; `cache-control: no-store`.
- The timeline queries are parameterized and capped at 20k rows per table. They include `engine` in the WHERE, so the primary key is used.
- The page:
  - escapes every session-derived value, including the `data-` attributes;
  - is served with a CSP: `default-src 'none'`, a hash for the one script and the one style, `connect-src 'self'`, `frame-ancestors 'none'`, `base-uri` and `form-action` set to `'none'`;
  - posts to exactly `https://ui.perfetto.dev`, never `*`;
  - checks that a PONG has that origin and that its data is `'PONG'`.
- The trace's metadata holds only session fields; no secrets.

**CI:**
- `grafana:check` runs as the read-only user, after `db:grafana-user` and `db:seed`. It executes every panel, annotation and query variable, in "All" and in single-value mode. Gaps: R-M2-13.
- It is deterministic: the seed is relative to now and the check uses each dashboard's own range.
- **Macro expansion.** I compared `macros.ts` with the plugin's expansions of `$__timeFilter`, `$__timeInterval`, `$__fromTime` / `$__toTime` and `$__interval_s`, and they match. I did not repeat the 18-macro comparison against a running Grafana.
