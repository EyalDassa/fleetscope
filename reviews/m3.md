## Must fix

### R-M3-01 Browsers dashboard mixes simulated and real data with no SIM label (data honesty). Owner: dashboard
`infra/grafana/dashboards/fleetscope-browsers.json` (panels 1-5, `source` variable defaults to All). Also `packages/db/README.md:698` (`engine-comparison`) and `compatibility-matrix`.
With the default `source = All`, the engine table, the bar gauges and the compatibility matrix blend sim and real sessions. Nothing on the panels says how much is simulated. Grafana Cloud is fed by `pnpm sim live` continuously, so on Cloud these numbers are mostly sim. Lightpanda and headless-shell are also `basis: "prior"` in `profile.json`, which makes their sim numbers assumptions, not measurements. The only hint is a sentence in the "How to read this" text. DESIGN.md §3 says simulated data is always labelled, and Overview has the Simulated share stat for exactly this reason.
**Fix:** add `round(100 * countIf(d.source = 'sim') / count(), 0) AS sim_share` to `per_engine` in `engine-comparison` and the same per cell in `compatibility-matrix`. Do it in the README snippet first, then in the panels. Show it as a "SIM share" column, `percent`, no colour, with the DESIGN mapping 0 → "0% · all real" and 100 → "100% · all simulated". Simpler alternative: add the Overview's Simulated share stat to the top row of Browsers, linked to Sessions with `var-source=sim`.

### R-M3-02 A stale Chromium image silently puts the forwarder back into Chromium's memory (fairness). Owner: backend
`apps/fleet-runner/src/docker.ts:373-377` and `apps/fleet-runner/src/engines.ts:70`.
When the sidecar's bind fails with `EADDRINUSE`, the runner treats it as "the browser image brings its own forwarder" and logs it at **debug** only. The revision-1 image (`fleetscope/playwright-chromium:1.64.1`) does exactly that. The legacy `FLEET_BROWSER_IMAGE` is still honoured as a fallback, and an M1/M2 `.env` sets it to `:1.64.1`. Such a developer runs the old image without noticing. Chromium's memory then includes the in-image forwarder again (ADR 0004: about 10-12 MB per sample), while the CDP engines don't. The `-2` revision was introduced to prevent this, but the tolerant path undoes it.
**Fix:** make `PORT_BUSY` a hard error ("port 3100 is already taken in the browser container: the browser image runs its own forwarder (stale image?), run pnpm browsers:build"). Alternatively, drop the `FLEET_BROWSER_IMAGE` fallback, or at least `warn` when it is used and its tag differs from `ENGINE_SPECS.chromium.defaultImage`. Update the comment at `docker.ts:356-360` and the matching test in `docker.sidecar.test.ts`.

### R-M3-03 Chromium's container memory still contains Playwright's Node `run-server` (fairness, undocumented). Owner: backend + dashboard
`infra/browsers/chromium/Dockerfile:63` (`ENTRYPOINT playwright run-server`), `apps/fleet-runner/src/docker.ts:264-272` (stats of the browser container only), and the Browsers "How to read this" text.
For `chromium`, the cgroup holds Chromium **plus a Node.js process** (Playwright's server). headless-shell and Lightpanda have only the browser. So the "Peak memory p50" for chromium is inflated by Node's RSS, most likely tens of MiB. That is larger than the forwarder that M3 moved out for fairness. The PR and ADR 0004 call the memory comparison fair, but this offset is not mentioned anywhere.
**Fix (minimum):** measure it. Take the first stats frame before `connect`, while only `run-server` is running, and record that figure. Then say it in the dashboard text, the README `peak_mem_mib_p50` row and ADR 0004 ("chromium includes Playwright's run-server, about N MiB idle"). **Better (can be M4):** run chromium like the others, with `chromium --headless --remote-debugging-port` and `connectOverCDP`, so all three engines are measured the same way. Unsure about the exact size, so measure before writing a number.

### R-M3-04 Simulator session ids are a function of the seed alone, so reusing a seed overwrites sessions. Owner: backend
`apps/simulator/src/generate.ts:98` (`session_id: sim-${rng.hex(8)}` from `sessionSeed(seed, index)`) and `apps/simulator/README.md:21` ("same sessions, same ids").
Running `pnpm sim run --seed 42` twice, or restarting `sim live --seed N` (a Cloud script will pin one), produces the same `session_id`s with new timestamps and new `event_id`s. `sessions` is a ReplacingMergeTree, so the second run **replaces** the first run's session rows. `actions`, `resource_samples`, `network_requests` and `issues` keep both copies, because their dedupe is on `event_id`. The session count drops while per-session actions, samples and cost double, and the dashboards disagree with each other. Also, `sessionSeed` is 32-bit, so different seeds can produce identical ids too (rare, but real over a long Cloud run).
**Fix:** `session_id: \`sim-${randomUUID()}\``. Keep the seed for the *content*, and say "same sessions, new ids" in the README. Add a test that two `planRun`s with the same seed have disjoint session ids.

### R-M3-05 (in progress, not landed) `heavy-page-crawl` probe: a timeout is counted as a missing API. Owner: backend
Working tree `apps/fleet-runner/src/scenarios/heavy-page-crawl.ts` (`failedProbes`) and `packages/collector/src/page.ts` (`extract` with `check`).
Every probe with `ok: false` makes the action fail with `unsupported_api`, including `"timeout after 3000ms"`. On a loaded machine (CI with `--concurrency 3`, `fleet traffic`), Chromium's `webWorker` probe can time out, and Chromium then shows up in the compatibility matrix as lacking Web Workers. That is a false engine verdict. The test at `scenarios.test.ts:285-294` actually locks this behaviour in.
**Fix:** only probe errors that show absence count as `unsupported_api`: an error that `isMissingApiError` accepts (ReferenceError, a TypeError naming a known API, the `crypto.subtle` read). A `timeout after` result is `timeout`; anything else is `js_error`. Change the test to expect `timeout` for the timeout case, and add a case with `"ReferenceError: Worker is not defined"` → `unsupported_api`.

### R-M3-06 Viewport fallback leaks a context, which Lightpanda's one-context limit should not tolerate. Owner: backend
`apps/fleet-runner/src/session-runner.ts:87-95`.
`browser.newContext({ viewport })` succeeds (the context is created), and the emulation call fails in `newPage()`. The catch then opens a **second** context without closing the first. Lightpanda allows one context per CDP connection, so the retry very likely fails, and the session's real error becomes "cannot create context". The catch also accepts *any* unsupported-feature error from `newPage`, then logs it as "refused viewport emulation" even when another CDP method was refused. Unsure whether 1.0.2 refuses `Emulation.setDeviceMetricsOverride` at all (if it doesn't, this path is dead code), but as written it cannot work on the engine it exists for.
**Fix:** keep the context in a variable, `await context.close().catch(() => {})` in the catch before the retry, and log the actual refused method (`error.message`). Add a unit test with a fake browser whose first `newPage` throws `Protocol error (Emulation.setDeviceMetricsOverride): ... wasn't found`.

### R-M3-07 CI Lightpanda relaxation is wider than its reason. Owner: platform
`.github/scripts/assert-fleet-smoke.sh:133-136`.
The reason given is "a session that ends at the bot wall may have no network row". But `eff_min_network=0` applies to **every** Lightpanda session, including successful ones. If Lightpanda's network capture breaks completely (no `Network.*` events at all), CI stays green. Nothing checks that Lightpanda can do anything, either: two sessions that each fail on their first `goto` pass.
**Fix:** inside awk, require `min_network` for a nullable engine unless the status is `blocked`. Also require at least one `ok` action per engine. This needs a `countIf(ok)` column in the `actions` subquery, and should be required at least for any non-`blocked` session.

### R-M3-08 `unsupported_feature` matches a bare "Method not found" anywhere. Owner: backend
`packages/collector/src/errors.ts:58`.
The comment says the wrapper ("Protocol error") or the -32601 code is required. The code also accepts a bare `Method not found` or `UnknownMethod`. A page's own JSON-RPC error thrown from `eval` (fallback `js_error`) or from an app call would be classified `unsupported_feature`, an engine limit that raises no issue. That is a mislabel in the compatibility matrix.
**Fix:** `if (/-32601/.test(message)) return true;` and move `Method not found|UnknownMethod` into the `Protocol error &&` branch. Add a test: `new Error("page.evaluate: Error: Method not found")` → not `unsupported_feature`.

## Should fix / nits

- **R-M3-09 (nit, backend)** `apps/simulator/src/cli.ts:136-143, 169`. On Ctrl+C, `live` posts in-flight sessions with **future** `ts`. With `--stretch`, these can exceed the API's 5-minute skew, and the API answers 400. A failed batch is logged and dropped, so its sessions stay `running` forever (the zombies R-M2-18 guards against). Fix: on stop, end in-flight sessions at `now` (clip `ts` to `now`). On a non-503 failure, still send each session's `session.ended`.
- **R-M3-10 (nit, backend)** `apps/simulator/src/generate.ts:23-31`. The `ISSUE_FOR_CODE` copy matches today but will drift. Fix: move `ERROR_CODES` and `ISSUE_FOR_CODE` (pure data, no Playwright) to `packages/schema`, re-export them from the collector, and type `ProfileFailure.error_code` as `ErrorCode`. Profile codes are then checked too.
- **R-M3-11 (nit, backend)** `apps/simulator/src/calibrate.ts:62-88`. The SQL lives outside `packages/db` (CLAUDE.md: all queries live there) and is unbounded: it reads all real rows ever into memory, and `fleet traffic` now grows that table daily. Fix: move it to `packages/db`, add `started_at >= now() - INTERVAL {days:UInt32} DAY` (default 14) and pass the value as a query parameter.
- **R-M3-12 (nit, backend; unsure)** `apps/simulator/src/profile.json:522`. The sim Lightpanda `engine_version` is `124.0.6367.29`, Chrome's number. The calibration therefore read real Lightpanda sessions whose version came from `browser.version()`, not `Lightpanda-Version`. Confirm that 1.0.2's `/json/version` really has the `Lightpanda-Version` key (`docker.ts:391-397`). Then re-calibrate, or override the version in `deriveEngine` when `basis = "prior"`. Add a smoke assertion that Lightpanda's `engine_version` doesn't start with a Chrome major version.
- **R-M3-13 (nit, dashboard)** `packages/db/README.md:691`. `action_p95_ms` includes failed actions. Lightpanda's failures are instant (-32601), and its failed sessions stop before the heavy steps, so its p95 looks better than its real page speed. Say so in the README row and in the "How to read this" text, or compute the p95 over `ok` actions (that needs a rollup column, so M4).
- **R-M3-14 (nit, platform)** `apps/fleet-runner/src/engines.ts:45,53` and `.env.example`. The upstream images are pinned by tag, and tags on Docker Hub are mutable. Consider `@sha256:` digests (`check-browser-images.sh` can accept `tag@digest`). Same for `fleetscope/forwarder:1`: bump the tag (or add a revision, like Chromium's) whenever `forward-port.mjs` or its Dockerfile changes, or a stale local sidecar is used.
- **R-M3-15 (nit, platform)** `infra/browsers/chromium/Dockerfile:36`. The two labels sit on one line, separated by spaces. That is valid, but it reads like a lost `\`. Split it.
- **R-M3-16 (nit, backend)** `docker.ts`. If the sidecar dies mid-session, the browser can't reach the demo site, and the session is recorded as an engine `nav_error`. Low probability. A cheap guard: after a failed session, inspect the sidecar, and if it exited, mark the reason `infra: forwarder exited`.

## Checked and fine
- **Engine table and connects.** Readiness is `/` for chromium and `/json/version` for the others. `connect` is used for Playwright's server, `connectOverCDP` with http for headless-shell and with ws for Lightpanda (avoids the in-container ws address). There is always a fresh `newContext()`. `LIGHTPANDA_DISABLE_TELEMETRY=true` is set. Ports are published on 127.0.0.1 only.
- **Sidecar lifecycle.** The browser is created, then the sidecar; removal is sidecar first, then the browser. On a failure, both readiness checks are awaited (`allSettled`) before cleanup. A dead browser is detected by `assertRunning`. Both containers carry the session, run and engine labels, plus `fleetscope.role`. The end-of-run sweep is scoped to `runId`. `cleanup` (all runs) is explicit and documented. Stats come from the browser container only. `startup_ms` stops when the browser answers, and the sidecar wait comes before `connect_ms` starts, so neither number includes it.
- **Fairness of assignment.** `assign.ts` takes `(seed + index) % (S*N)`, which is scenario-major, so every block of S*N sessions covers every pair exactly once. The tests cover 5 seeds. CI's 6 sessions give exactly 2 per engine for any seed. Time to browser is defined as `startup_ms + connect_ms`, and the docs and dashboard explain that only the sum compares.
- **Error classification.** The known-API TypeError list is narrow and anchored, so a normal app TypeError stays `js_error`. `unsupported_feature` raises no issue (consistent with the sim copy).
- **SQL.** `session-facts` has the 1-day lower bound, documented with its trade-off. The engine/source push-down is in `issue_facts` and `action_facts`. The Session-detail exception in `session-facts.ts` is limited to those two lines, those two CTEs and `fleetscope-session` only, with tests for the negative cases. In `engine-comparison`, NULL vs 0 is handled through counts (memory NULL without container samples, cost NULL if any session is unpriced, latency NULL without actions, heap shown as "Not available"). Time series come from `fleet_minute`. Everything is bounded by the time range. The matrix shows "—" for a cell that didn't run, never 0%.
- **Simulator.** Every batch is validated with `EventBatch` before posting. Sessions are never split across batches. The run backfill is kept in the past. `live` pending memory is bounded by session length. Priors are documented and marked `basis: "prior"`.
- **CI and secrets.** The image-tag consistency check works and rejects `latest`. Upstream images are pulled with retries, and the forwarder build uses the gha cache. Dependabot covers the forwarder base image, minor versions only. `testPassword()` is random. Dev defaults live in one module and are only tried against loopback. No secrets in the diff.

### New findings in round 2 (all nits, none blocking)

- **R2-01 (nit, dashboard)** `infra/grafana/dashboards/fleetscope-browsers.json`, "How to read this" (panel 6) and the description of "p95 action latency" (panel near line 1096). Add the README's caveat in one line: "p95 includes failed actions; an engine that fails fast can look faster, so read it next to success rate." This finishes R-M3-13.
- **R2-02 (nit, dashboard)** `packages/db/README.md`, row `peak_mem_mib_p50`. Add "chromium includes Playwright's run-server, ~110 MB (ADR 0004 item 5, M4)" so the snippet docs match the dashboard and the ADR.
- **R2-03 (nit, backend)** `apps/fleet-runner/src/session-runner.ts`, the `forwarderExited()` check. It is awaited without `bounded(...)`, while every other Docker call at the end of a session is bounded. A hung `inspect` would stall that session's finish. Wrap it in a short timeout (treat a timeout as `false`). Also note that the session still counts as `failed` for the engine (and its action keeps `nav_error`), so it lowers the engine's success rate. That is acceptable as long as it is rare. If it ever matters, use `infra_error`-style handling in M4.
- **R2-04 (nit, dashboard; unsure it is worth it)** The "Simulated share" value mappings match exactly 0 and 100. A share of 99.6 renders as "100%" without "all simulated", and 0.4 as "0%" without "all real". That is technically honest, but the label could read as stronger than the data. Use 1 decimal, or a range mapping for (0, 1) → "<1%" and (99, 100) → ">99%".

No regressions found in the fixed code paths. QA's open items QA-M3-01/02/03 are fixed on the branch: lint is green, the simulator has 25/25, and `sim live` exits 130.
