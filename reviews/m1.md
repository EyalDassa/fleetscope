## Findings (most severe first)

### R-M1-01 Two kinds of validated event make ClickHouse refuse a flush forever, which stalls ingest for every client (must fix, backend-ingest + backend-fleet)

**Where:**
- `packages/schema/src/events.ts:76-78` (`id`, `label`, `text`) and `:95-97` (`TS_MIN` is 2020-01-01).
- `apps/api/src/ingest/validate.ts:55` (only a future bound).
- `apps/api/src/ingest/buffer.ts:308-326` (retries forever).
- `docs/adr/0002-ingest-dedupe.md:102-104`.
- Collector string cuts: `packages/collector/src/session.ts:39-40` (`clip`), `errors.ts:56` (`shortMessage`), `page.ts:281` (`pageerror`), `page.ts:340-342` (`domainOf`).

**Problem:** ADR 0002 accepts a stalled buffer because "validated events should never be refused". Here are two counterexamples. Both pass `checkBatch` (I ran it with tsx), and ClickHouse 26.8 rejects both.

1. **A lone UTF-16 surrogate in any string.**
   - `z.string()` accepts `"boom \ud83d"`. `JSON.stringify` sends it as `\ud83d`, and ClickHouse answers code 25 `CANNOT_PARSE_ESCAPE_SEQUENCE` every time.
   - Our own collector can produce one. `clip()`, `shortMessage()`, the `pageerror` `.slice(0, 500)` and `domainOf()` cut by UTF-16 code unit, so cutting through an emoji leaves half a pair.
   - Any page the fleet visits can produce one on purpose: `throw new ReferenceError("\ud800")` lands in `issue.message`.
2. **More than 100 days in one flush.** `ts` may go back to 2020, and the raw tables are partitioned by day. A flush that touches more than 100 distinct days exceeds `max_partitions_per_insert_block = 100`, and ClickHouse throws on every attempt. 101 events, one per day, are enough; I confirmed `checkBatch` accepts them.

**What happens next:**
- `writeUntilStored` retries that flush forever, and everything behind it waits.
- The buffer fills to 50,000 events. Then every client gets `503`, and the collectors start dropping batches (R-M1-03).
- A restart doesn't help. Shutdown can't flush the poisoned batch either, so up to 50,000 events that were already acknowledged are lost.

One misbehaving client, or one hostile web page, can take down ingestion for everyone.

**Fix:**
- **Schema (backend-ingest):** reject or repair lone surrogates in the string building blocks. Either `.refine((s) => s.isWellFormed(), "contains an unpaired surrogate")` or normalize with `s.toWellFormed()` (Node 20+, needs `lib: ES2024`). Test with `"\ud83d"` in `issue.message` and in `action.target`.
- **Validation (backend-ingest):** also reject a `ts` older than the raw-table TTL (`now - 30 days`; 7 days is fine too). Answer 400 and name the indexes, like the future-skew check. Such rows would be deleted by TTL anyway, and the bound caps a flush at about 31 daily partitions. Test with 101 distinct days.
- **Collector (backend-fleet):** make `clip`, `shortMessage`, the `pageerror` slice and `domainOf` surrogate-safe. Call `.toWellFormed()` after slicing, or drop a trailing high surrogate.
- **ADR 0002:** replace "should never be refused" with these two guards, and record the decision on the safety valve below.
- **Safety valve (lead decides):** an unknown future data error would still stall everything.
  - I recommend this: when ClickHouse returns a data or parse error for the same flush 5 times, log the flush's event ids and session ids at `error` level (or write the batch to a dead-letter file). Then drop the flush and count it as `deadLettered` in `/healthz`.
  - The error codes that qualify: `6 CANNOT_PARSE_TEXT`, `25`, `26`, `27`, `53 TYPE_MISMATCH`, `117 INCORRECT_DATA`, and `252 TOO_MANY_PARTS` only when the message mentions partitions.
  - Network errors and merge backpressure don't qualify.
  - Dropping one batch loudly, with a count, beats an outage for every client.

### R-M1-02 Every browser container shares the host's IPC namespace (`IpcMode: "host"`) (must fix, backend-fleet; platform for the Dockerfile comment)

**Where:** `apps/fleet-runner/src/docker.ts:115`, and the run-by-hand example in `infra/browsers/chromium/Dockerfile:9`. Compare `infra/browsers/README.md:65-68`.

**Problem:** The code comment says "Chromium needs a big /dev/shm". But playwright-core 1.64.1 already starts Chromium with `--disable-dev-shm-usage` (`chromiumSwitches` in `lib/coreBundle.js`), as the platform README says. So the setting buys nothing. Here is what it costs:
- **Isolation.** The same Playwright code launches Chromium with `--no-sandbox` (whenever `chromiumSandbox !== true`). The container is therefore the only barrier between page content and the machine. `--ipc=host` gives every session the host's System V IPC and POSIX message queues, and mounts the host's `/dev/shm`. On Linux CI that is the runner itself; on Docker Desktop it is the VM.
- **Leaks between sessions.** Whatever a session leaves in `/dev/shm` outlives its container. With a private namespace, `/dev/shm` dies with the container. Today's setup breaks decision 1 ("no state leaking between sessions"). It also blurs attribution: memory charged to a removed container's cgroup moves to the parent cgroup, so no session owns it.

**Fix:**
- Remove `IpcMode: "host"`.
- Remove `--ipc=host` from the Dockerfile comment.
- If crashes ever show up under load, set a per-container `ShmSize` (for example 256 MB) instead.
- Assert in `docker.test.ts` that `HostConfig.IpcMode` is not `host`.
- Re-run the 10-session check.

### R-M1-03 The collector drops a batch after about 13–26 s of retries, `session.started`/`session.ended` included (must fix, backend-fleet)

**Where:** `packages/collector/src/transport.ts:86-90` and `:108-155`; `packages/collector/src/queue.ts:14-19` and `:134-158` (the drop is at `:144`).

**Problem:** To answer "can `session.ended` be lost?": yes, in three ways. All three are counted and logged, and the run exits 1.
- (a) **Retries run out.** There are 8 attempts, so 7 sleeps with ceilings from 250 ms to 10 s. That adds up to about 13–26 s for network errors, and exactly 14 s when the API answers `503` with `Retry-After: 2`.
- (b) **`close()` hits its 10 s deadline.**
- (c) **The batch gets a 400** (R-M1-10).

(a) is a design bug. `maxBuffered` (100,000 events, dropping samples first) is documented as the bound "when the API is unreachable for a long time". With the attempt cap, nothing ever piles up: after about 20 s the batch at the head of the queue is dropped and the next one is tried. So an API restart, a deploy, or a full API buffer that lasts longer than that loses the sessions that started or ended in that window.

A lost `session.started` is especially bad. The matching `session.ended` becomes an orphan, which the API drops after 60 s. The session then never appears in `sessions`, although its actions and samples are stored.

**Fix:**
- While the collector is open, a `failed` send is not final. Put the batch back at the head of the buffer (this keeps the order) and keep retrying with the capped backoff. That lets `maxBuffered` do its job.
- Give up only at the `close()` deadline, or after a total retry time below the API's 15-minute duplicate window (for example 10 minutes), so a late resend is still recognised as a duplicate.
- Test it: the API is down for 60 s, then comes back. Every event must arrive, in order, and nothing is dropped.

### R-M1-04 When a click leads to a 403 or 500 page, the session ends as `failed` / `selector_not_found` instead of `blocked` (must fix, backend-fleet)

**Where:** `packages/collector/src/page.ts:142-149` (`click`) and `:256-264` (`throwIfCaptcha`). The 403 check exists only in `goto`, at `:132`.

**Problem:** The main document's status is only checked in `goto`.
- A `click` can navigate too: a link, or a form post that redirects with 303 to a GET. If it lands on the demo site's 403 bot wall, that page has `data-testid=botwall-blocked`, not `captcha`.
- So the click is recorded `ok: true`, and no `blocked` issue is raised. The next action fails after 10 s with `selector_not_found`, and the session ends `failed`.
- The same happens with the global `errorRate`: the 500 page raises no `nav_error` issue.
- This is exactly what the contract's global chaos (`POST /admin/chaos {"botwallRate":0.3}`) produces, and that is how a demo will switch chaos on.

Showing a blocked session as failed breaks the data-honesty rule. It also makes the M3/M4 "block or CAPTCHA rate per domain" insight undercount.

**Fix:**
- In `listen()`, record the status of main-frame navigation responses: `page.on("response", (r) => { if (r.request().isNavigationRequest() && r.frame() === page.mainFrame()) … })`.
- In `click`, and in `goto` too so there is one code path, check that status after the load state when it came from a navigation during this action. Throw `BlockedError("http_403")` for a 403 and `CollectedError("nav_error")` for any other status of 400 or more.
- Test: click a link whose target answers 403. The action must fail with `http_403`, a `blocked` issue must appear, and the session must end `blocked`.

### R-M1-05 What `startup_ms` and `connect_ms` measure is undocumented, and the existing docs say otherwise (must fix, backend-ingest + backend-fleet; lead for PLAN)

**Where:** `packages/schema/src/events.ts:122-125`; `packages/collector/src/session.ts:128`; `apps/fleet-runner/src/session-runner.ts:116-125`; PLAN section 3.

**Problem:** `playwright run-server` launches a browser for each client connection. So in M1:
- `startup_ms` runs from container create until the server answers. **No browser exists yet.**
- `connect_ms` is `chromium.connect`, which **includes launching Chromium**.

The docs say otherwise:
- The schema calls `startup_ms` "Time to start the browser", and `connect_ms` "Time to connect the client".
- `session.ts:128` says "browser startup is reported separately as `startup_ms`".

This matters in M3. A CDP engine (headless-shell, Lightpanda) starts its browser before its endpoint answers, so its launch time lands in `startup_ms`. A "startup" column on /browsers would then compare Chromium without its launch against the other engines with theirs.

**Fix:** Write the meaning into the schema comments, which are the contract:
- `startup_ms`: container create until the engine's endpoint answers. For a Playwright server, no browser exists yet.
- `connect_ms`: client connect until a browser is ready. For a Playwright server, this includes the browser launch.

Also fix `session.ts:128`, and add one line to PLAN section 3: engines are compared on `startup_ms + connect_ms`. Schema v1 itself doesn't change.

### R-M1-06 The Node forwarder's memory is in every session's numbers, but the README says the comparison "stays fair" (must fix, docs only in M1; platform)

**Where:** `infra/browsers/README.md:93-95`; `infra/browsers/chromium/entrypoint.sh`.

**Problem:**
- The forwarder is a Node process in the container's cgroup. So every container sample includes its memory, and its CPU too: it proxies every byte of page traffic, such as the 200 image requests of `/heavy`.
- An idle Node process takes roughly tens of MB. I'm unsure of the exact number, so it needs measuring.
- For Chromium (hundreds of MB per session) that is noise. For M3 it isn't, because Lightpanda's whole footprint is in the same tens-of-MB range.
- Adding the same constant to both engines doesn't keep the comparison fair. It shrinks the ratio between them, which is the headline number of the /browsers page.
- The Lightpanda image would also need Node added just for the forwarder.

**Fix (M1):**
- Replace "stays fair" with the measured baseline, for example `ps -o rss` for the forwarder inside an idle container, next to `docker stats`.
- State that this baseline is included in every container sample.
- Record the M3 plan now, in PLAN section 3 or an ADR.
  - My preference: a **sidecar** forwarder container per session that joins the browser container's network namespace (`NetworkMode: container:<id>`). `localhost:3100` still works, and the forwarder's CPU and memory go to the sidecar's own cgroup instead of the session's.
  - The alternative: a native forwarder of about 1 MB, such as `socat`, in every image, with its cost documented.

### R-M1-07 Samples taken before the session started are stamped when they are handed over, not when they were read (nit, backend-fleet)

**Where:** `apps/fleet-runner/src/stats.ts:140-143` and `:229-230`; `packages/collector/src/session.ts:116` (no `ts`, so `emit` uses `Date.now()`); `session-runner.ts:122` and `:157`.

**Problem:** Polling starts as soon as the server answers, while `chromium.connect` is still launching Chromium.
- Readings from that time are held until `attach()`, and then all get `ts = now`. On a slow machine, two readings can end up with the same timestamp.
- The first reading averages over the Chromium launch, which is the CPU spike of the session.
- Charging the launch to the session is honest, because the container exists only for that session. Hiding when the reading was taken is not: short sessions will show "peak CPU at 0 s", and that peak is the launch, not the scenario.

**Fix:**
- Add `readAt` (when the stats call returned) to `ContainerSample`, and pass it as `ts` in `recordContainerSample`.
- Keep only the newest held reading, with its real time. That time can be up to `connect_ms` before `started_at`.
- Document that the first container sample covers the browser launch.

### R-M1-08 Container network bytes include the automation channel (nit, backend-fleet, docs)

**Where:** `apps/fleet-runner/src/stats.ts:69-79` and the class comment at `:101-112`.

**Problem:**
- The delta math is right, including the reset when a counter goes down.
- But the runner talks to `run-server` through the published port, so that traffic also crosses the container's `eth0`. Every Playwright protocol message and every screenshot PNG is counted along with the page traffic.
- The Playwright protocol (Chromium) and CDP (the M3 engines) send different volumes. So per-engine "bandwidth" will differ for reasons that have nothing to do with the pages.

**Fix:** Document it in `stats.ts` and in the field doc: these numbers are container network bytes, not page bytes. M2 should label bandwidth cost that way, or compute it from `network_requests.bytes`, scaled up because requests are sampled 1 in 5.

### R-M1-09 Each session's unauthenticated `run-server` is reachable from the other browser containers (nit now, must fix before the fleet browses third-party sites; backend-fleet)

**Where:** `apps/fleet-runner/src/docker.ts:108-121` (no `NetworkMode`, so the default `bridge`); `entrypoint.sh` starts the server with `--host 0.0.0.0`.

**Problem:**
- The host side is right: the port is published on `127.0.0.1` only.
- Inside Docker, though, `run-server` listens on `0.0.0.0` on the default bridge, and that bridge lets containers talk to each other.
- A page in session A runs in Chromium without a sandbox (see R-M1-02). It can open `ws://<B's IP>:3000/` and drive a browser in session B's container.
- M1 only browses our own demo site, so this can't happen today.

**Fix:** In `DockerFleet`, create a `fleetscope-browsers` network once, with `com.docker.network.bridge.enable_icc=false`, and attach every browser container to it. `host-gateway` and port publishing work the same on a user-defined bridge.

### R-M1-10 One bad event drops a whole 1000-event batch from every concurrent session (nit, backend-fleet)

**Where:** `packages/collector/src/queue.ts:134-158`; `transport.ts:134-143`.

**Problem:** All sessions of an engine share one queue. A 400 drops the whole batch, including other sessions' `session.started`/`ended`, even though the API's `issues[].path[0]` names the bad events.

**Fix:** When every issue in a 400 has a numeric `path[0]`, drop and log only those events, and send the rest once more. Otherwise keep today's behavior.

### R-M1-15 Fleet smoke: gaps in what it asserts, and how it can turn red for no real reason (nit, platform)

**Where:** `.github/scripts/assert-fleet-smoke.sh:31`, `:39`, `:57-68`; `.github/workflows/ci.yml:147`.

**Problem:**
- `min_actions = 3` applies to every session. A `checkout-form` session that hits the 20% bot wall on its first `goto` has only 1 action. With `--seed 1` it passes today. But any change in how the RNG is consumed (a new `rng` call in a scenario, or a different dice order in the demo site) re-rolls that 20% chance, and CI goes red for an unrelated reason.
- `uniqExact(event_id)` hides duplicate rows, although dedupe is the central M1 decision.
- The M1 "done when" requires cdp samples and network requests, and neither is checked.

The rest is sound: Docker actions pinned to SHAs, `ignore-error` on the cache export, step and job timeouts, logs uploaded on failure, and a leaked-container check.

**Fix:**
- Require `min_actions` only for `success` sessions, and at least 1 action for the others.
- Assert `count() = uniqExact(event_id)` for each table.
- Assert at least one `origin = 'cdp'` sample and at least one `network_requests` row per session. Both are guaranteed: the heap sampler reads once at attach, and the first request is always sampled.

## Answers to the lead's questions

When no finding is named, the answer is "fine".

- **Buffer.**
  - Ordering is correct: one flush at a time, cut from the head, and retries resend the same `Flush`.
  - Flush and enqueue can't interleave, because `offer` is synchronous.
  - Memory is bounded: `queued` counts pending, in-flight and held orphans.
  - The 503 path checks capacity before `recentIds.add`, and a test covers it.
  - Shutdown runs in the right order. Fastify's own close hook stops the server and lets in-flight requests finish, then `buffer.close()` runs, then `client.close()`. Tests cover it.
  - The poison batch is R-M1-01.
- **Dedupe.**
  - The token semantics hold on 26.8, as the ADR describes.
  - `'disable'` on inserts without a token only affects those inserts. I found no side effect, and the seed stays repeatable.
  - A batch that spans several partitions gets one block per partition, each with a token derived from the flush token. The split is the same for the same rows, and `dedupe.integration.test.ts` covers it.
  - 10,000 blocks per table is plenty. Even at R-M1-01's cap of about 31 partitions per flush, that is more than 5 minutes of flushes, and hours in practice. During a retry nothing new is written, so the window doesn't move.
- **Collector transport.**
  - Retry bounds and how `session.ended` can be lost: R-M1-03 and R-M1-10.
  - Event order holds: one drain loop per collector, and one collector per engine.
  - `session.ended` is sent only after `poller.stop()` (bounded at 2.5 s) and a final heap reading (bounded at 500 ms). The `ended` flag drops anything that arrives after it.
  - The order can only break when a batch is dropped.
- **Stats math.**
  - CPU = `cpu_delta / system_delta × online_cpus × 100`, falling back to `percpu_usage.length` for the CPU count. That is the docker CLI formula, and with `stream: false` the daemon fills in `precpu_stats` first.
  - Memory = usage minus `inactive_file` (cgroup v2) or `total_inactive_file` (v1). Correct.
  - Network deltas are correct, but see R-M1-08.
  - The held first sample is R-M1-07.
- **Container security.**
  - Publishing `run-server` on `127.0.0.1` only is correct.
  - `--ipc=host`: it weakens both isolation and attribution, and it isn't needed (R-M1-02).
  - Container-to-container access: R-M1-09.
  - The demo site's admin API: R-M1-16.
- **Measurement honesty.** The forwarder is R-M1-06. `connect_ms` includes the browser launch and that isn't documented (R-M1-05).
- **CI.**
  - The smoke job is deterministic for a given commit: `--seed 1`, seeded chaos, step and job timeouts.
  - The Docker actions that get tokens are pinned to SHAs. First-party `actions/*` stay on tags, per the M0 convention.
  - The assertions are R-M1-15.
- **Readability.** Good. Non-obvious choices have a comment that explains why: the BuildKit chmod story, the encoded-size chunking, the shutdown order. Nothing clever needs simplifying. `buffer.ts` is the longest file; its diagram and the "Rules that make it safe" list are what Eyal should walk through in the interview.
